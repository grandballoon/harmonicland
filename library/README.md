# Score library

Solo-piano scores captured from open sources, kept byte-for-byte as published, and converted to MusicXML the app can load.

## Files

- `pieces.json` is hand-written: which pieces, which sources, the commit each GitHub source is pinned to, and any per-source conversion choice (with its reason).
- `sources/` holds the downloaded files, laid out by origin (`sources/github/<owner>/<repo>/<path>`, or the host name for non-GitHub sources).
- `manifest.json` is generated by `tools/library/fetch.ts`; do not edit it by hand.
  It records every file's URL, SHA-256, and the license, title, and copyright the file states about itself.
- `scores/<piece>/<source>.musicxml` are generated by `tools/library/convert.ts`; do not edit them by hand.
- `scores/report.json` is generated alongside them: per file, the source, every warning, and the verification result.
- `build/` is scratch space for the tools (LilyPond runs, witness MIDI, the MusicXML schema) and is not committed.

To refetch, run `node tools/library/fetch.ts` with Node 22 or newer.
To reconvert, run `node --import ./tools/library/extensionless.ts tools/library/convert.ts`, optionally followed by piece ids.
Conversion needs LilyPond 2.26 (`lilypond` and `convert-ly` on the path) and `xmllint`.

## Sources and licenses

Only KernScores, Mutopia, and ASAP are used.
Nothing is taken from musescore.com.

- Mutopia files are Public Domain, CC BY, or CC BY-SA, stated per file.
- KernScores licenses vary per file: CC BY-NC-SA 4.0 (Mozart), "rights to derivative editions reserved" (CCARH Bach), or unstated (treat as non-commercial research use).
- ASAP is CC BY-NC-SA 4.0 as a whole dataset.

Where a piece has several sources, all are kept so encodings and historical editions can be compared before one is chosen.
Each converted file's `<rights>` and `<source>` carry its license and pinned source URL.

## How LilyPond sources are converted

Nothing re-parses LilyPond syntax.
LilyPond itself reads each file, and a hook loaded before it (`tools/library/lilypond/dump.ly`) records what LilyPond decided: every music event with its exact moment, the clef and key in force, the bar positions, and the engraving decisions events do not carry (printed accidentals, beams, ties, barlines).
`to-score.ts` turns that record into notation and `musicxml.ts` writes it as MusicXML 4.0.

Before LilyPond runs, a copy of the source (never the source itself) is upgraded to current syntax by `convert-ly`, plus the few rewrites in `compat.ts` that `convert-ly` lacks.
Every rewrite is a change of spelling, not of music, and each one applied is listed in the report and in the file's `<encoding-description>`.

## How conversions are checked

Every file is checked three ways when it is made, and fails the run if any check fails.

1. It validates against the W3C MusicXML 4.0 schema.
2. It is read by the app's own `MusicxmlIn` and compared with LilyPond's performance of the same music, read by the app's own `MidiIn`: every note's pitch, onset, length, and hand, and the grace notes pitch for pitch.
   The performance comes from LilyPond's MIDI performers, independent of the recorded events, with tempo and articulation shortening removed so it states written time.
3. The conversion refuses anything it cannot place: an unknown event, articulation, or markup command is an error, never a silent drop.

Judgement calls are recorded as warnings in the report, for example a mark written on a spacer rest placed on the note it sits over, or a note LilyPond let run through a barline written as tied notes.
`tools/library/library.test.ts` re-reads every converted file in the test suite, so the library stays loadable as the app's parser changes.

Verovio, which reads MusicXML natively, loads every file with its note count intact.
It does not draw slurs that cross between staves or pedal changes on consecutive downbeats; both are valid MusicXML and are drawn by other readers.
